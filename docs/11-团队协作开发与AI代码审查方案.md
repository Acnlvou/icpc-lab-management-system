## 一、文件所有权边界（防止多人改同一文件产生冲突）

为了避免 4 人并行开发时在 `models.py`、`schemas.py`、`router.js` 上反复冲突，实行**按模块拆文件**策略：

| 成员 | 功能分支 | 专属新增文件（零冲突） | 仅需追加挂载的公共文件（1~2行） |
| :--- | :--- | :--- | :--- |
| **李靖宇** | `feature/training-camp` | `backend/app/routers/training.py`（日常训练+寒暑假集训） | `models.py`、`schemas.py`、`main.py`（优先合入 `develop`） |
| **莫 姝** | `feature/team-contest` | `backend/app/routers/contest.py`（组队+校赛+非XCPC+XCPC） | `models.py`、`schemas.py`、`main.py`、`seed.py`（在李靖宇合入后 rebase/pull） |
| **尚思彤** | `feature/frontend-training`（训练+竞赛单分支交付） | `frontend/src/views/TrainingView.vue`<br>`frontend/src/views/ContestView.vue` | `frontend/src/api/client.js`、`router.js`、`App.vue`、`DashboardView.vue` |
| **覃爽爽** | `feature/qa-acceptance` | `backend/tests/test_sprint3_4.py`（独立测试文件，不撞 `test_api.py`） | `docs/08-迭代任务拆分与测试验收报告.md` |

> **核心防冲突顺序**：
> 1. 先冻结下方 Sprint 3/4 接口路径与字段契约；
> 2. 后端两位成员（李靖宇、莫姝）各自写独立路由文件，谁先完成先合并进 `develop`，另一位 `git pull origin develop` 后再合入；
> 3. 前端（尚思彤）可对照契约同步写页面，后端合入 `develop` 后拉取联调；
> 4. 测试（覃爽爽）在独立测试文件里编写 `BR-007 ~ BR-010` 自动化用例。

> **跨分支边界与版本升级裁决**：
> - 前端分支严禁改动 `backend/app/main.py`、`backend/app/routers/dashboard.py`、`backend/tests/test_api.py`；
> - 在 `#1`（`feature/training-camp`）与 `#2`（`feature/team-contest`）合入 `develop` 前，系统进度与版本统一保持 `50%` / `v0.5.0-milestone`，合入后再由组长（李靖宇）统一升级为 `100%` / `v1.0.0` 并接入训练/赛事 KPI。

## 二、Sprint 3 & Sprint 4 冻结接口契约（前后端先对齐再写代码）

> **字段级入参/出参唯一事实来源**：所有请求体、查询参数、响应模型与枚举值均以 [`.spec/api.spec.yaml`](../.spec/api.spec.yaml) 中的 `components.schemas` 为准（已对齐前端 `docs/13` 第 2 节）。

### Sprint 3：训练与集训管理（`/api/v1/training`）
- `GET/POST /api/v1/training/plans` — 整体训练计划 & 个人补强训练规划（创建个人计划时自动读取该成员最近一次个人能力评估的 `weak_points` 并留存 `source_assessment_id` 快照，非竞赛会员建个人计划返回 `400`，落地 **BR-007**）
- `GET/POST /api/v1/training/tasks` — 训练任务下发（支持直接关联题库 `problem_list_id`）
- `POST /api/v1/training/tasks/{id}/checkin` — 记录训练完成度、考勤状态（`PRESENT`/`LATE`/`ABSENT`）、补题数与反馈
- `GET/POST /api/v1/training/camps` — 寒假集训（`WINTER`）与暑假多校集训（`SUMMER`）记录（暑期集训按 **BR-008** 必须关联非空 `team_id`）
- `POST /api/v1/training/camps/{id}/summary` — 记录集训总结与阶段复盘，衔接下一轮能力评估

### Sprint 4：队伍与竞赛管理（`/api/v1/contest`）
- `GET/POST /api/v1/contest/teams` — 队伍档案管理（入队留存成员六维能力快照）；`GET /api/v1/contest/teams/recommend` 基于竞赛会员六维能力画像返回能力互补候选组合
- `GET /api/v1/contest/teams/{id}` — 获取队伍完整档案（成员快照、调整流水、关联暑期集训与 XCPC 成绩）
- `POST /api/v1/contest/teams/{id}/adjust` — 追加队伍成员调整历史（`ADD`/`REMOVE`/`REPLACE`，不覆写过往成绩，落地 **BR-008**）
- `GET/POST /api/v1/contest/school-contests` — 校赛方案列表与创建
- `GET/POST /api/v1/contest/school-contests/{id}/entries` — 查询与录入校赛个人选手报名、初赛排名与成绩（个人制 `member_id`）
- `POST /api/v1/contest/school-contests/{id}/confirm` — 决赛参赛确认；放弃或逾期（`auto=True`）时同事务按 `prelim_rank` 升序触发**候补递补**，重复确认返回 `400`（落地 **BR-009**）
- `GET/POST /api/v1/contest/school-contests/{id}/anomalies` — 查询与登记线上初赛异常行为核查材料，初始状态固定 `PENDING_REVIEW`（落地 **BR-010**）
- `PUT /api/v1/contest/school-contests/{id}/anomalies/{anomaly_id}/review` — 人工填写最终三值复核结论（`CONFIRMED_VIOLATION`/`EXONERATED`/`NEED_MORE_EVIDENCE`），不覆盖原始材料（落地 **BR-010**）
- `GET/POST /api/v1/contest/non-xcpc` — 蓝桥杯/天梯赛/码蹄杯/百度之星赛事与个人成绩归档（个人制 `member_id`）
- `GET/POST /api/v1/contest/xcpc` — XCPC 网络预选赛、队伍综合排序、正赛赛站名额与结果（`team_id` 非空关联队伍档案，落地 **BR-008**）

### 字段级契约关键约定
1. JSON 字段统一使用 `snake_case`，后端 Pydantic Schema 与响应字段严格按 `.spec/api.spec.yaml` 的 `components.schemas` 命名；
2. 校赛放弃参赛状态统一锁定为 **`ABANDONED`**（禁止使用 `DECLINED`）；
3. `POST /api/v1/training/camps` 接收 `team_id` 字段，且当 `camp_type == "SUMMER"` 时按 **BR-008** 必填非空；
4. `GET /api/v1/contest/teams/recommend` 必须在路由文件中声明在 `GET /api/v1/contest/teams/{id}` 之前；
5. 后端 ORM 模型类名统一约定为 `TrainingPlan`、`TrainingTask`、`TrainingCamp`（李靖宇）与 `Team`、`SchoolContest`、`XcpcResult`、`NonXcpcResult`（莫姝），方便后续统一升级 Dashboard KPI。

## 三、组员每日开发标准 6 步操作（可直接发给组员照抄）

```bash
# 1. 首次克隆仓库（只需做一次）
git clone https://github.com/Acnlvou/icpc-lab-management-system.git
cd icpc-lab-management-system

# 2. 每次开新任务前，先同步最新的 develop 分支
git checkout develop
git pull origin develop

# 3. 切出自己的功能分支（严禁直接在 main 或 develop 上写代码！）
git checkout -b feature/你的模块名

# 4. 写完一个小功能就本地自测并提交（遵循 Conventional Commits，提交说明统一用中文）
ruff check backend                                  # 改了后端必跑
cd backend && PYTHONPATH=. .venv/bin/pytest -v      # 改了后端必跑
npm --prefix frontend run build                     # 改了前端必跑

git add <你改动的文件>
git commit -m "feat(training): 新增关联能力薄弱项的个人训练计划接口"

# 5. 推送到你的远程功能分支
git push -u origin feature/你的模块名
```

6. 打开 GitHub 仓库页面，点击黄色提示条 **`Compare & pull request`**：
   - **base** 选 **`develop`**（⚠️ 不要直接提往 `main`！）
   - 按自动弹出的 PR 模板填好关联的 `Closes #x` 和自检清单
   - 等待页面下方 **GitHub Actions CI（Ruff + Pytest + Vue Build）全部变绿 ✅**，并在群里 @组长 安排 Agent 审查。

## 四、组长 + Agent 双重代码审查 SOP（你这边怎么用我省心把关）

现在仓库已经配置了 **两道防线**：

### 第一道防线：GitHub Actions 自动 CI（全自动，零人工成本）
组员一提 PR，GitHub 云端会自动执行 `.github/workflows/ci.yml`：
- 自动跑 `ruff check backend`
- 自动跑 `pytest -v`
- 自动跑 `npm run build`
> **铁律**：CI 没全绿的 PR 直接打回让组员修，不浪费人工或 Agent 审查时间。

### 第二道防线：你的 Agent 深度规范审查（1 句话触发）
当某个 PR（例如 `PR #5`）CI 全绿后，你只需要在对话里直接跟我说一句：
> **“帮我审查一下 PR #5”**

我就会自动通过 `gh pr view 5` 和 `gh pr diff 5` 拉取完整改动，按以下 5 条 SDD 红线逐行审查：
1. **规范一致性**：是否严格满足 `BR-001 ~ BR-010`（如 BR-007/008/009/010 状态边界有无越权或漏判）？
2. **契约与类型安全**：Pydantic Schema、HTTP 状态码、SQLite 外键级联、Python 3.9 兼容性有无隐患？
3. **前后端联调**：前端调用路径、参数字段名与后端是否完全对得上？
4. **测试覆盖**：是否补齐了对应业务规则的 `pytest` 用例？
5. **污染检查**：有无误提交 `.db`、`.venv`、`node_modules` 或无关文件？

审查完后，我会给你一份清晰的审查结论，并可经你确认后直接用 `gh pr review` 把审查意见发到 GitHub PR 页面上（**这在最终报告“工程管理过程及版本控制”里是非常亮眼的真实 Code Review 留档！**），确认无误后一键 Merge 进 `develop`。
